Native auth and modular JS database operations can therefore use different Firebase projects inside one app. The shared-infrastructure assumption is not true for all SDKs in these checkouts.

Before integrating data, trace each Auth and Firestore call to its SDK, identify the deployed production project and UID population, and verify the deployed rules. Do not change Firebase client IDs as a shortcut: this can strand existing users or route writes into a different database. Do not deploy Fynage's local rules as a replacement for shared production rules. Tengesa's rules file is explicitly a merge fragment and is not attached to its Firebase deployment config.

## Safe integration plan

1. **Inventory and preserve:** record deployed project IDs, Auth providers/UIDs, rule versions, collection counts, and financial totals for every app. Export backups; do not move or rewrite existing records.
2. **Choose identity topology:** either converge on a single Auth/Firestore project through a separately planned migration, or keep the projects federated and use authenticated, server-to-server adapters. Document the canonical user/business mapping; matching phone numbers alone is insufficient.
3. **Define authorization:** create immutable business/account IDs and top-level `memberships` keyed by business and user, with app scope, role, explicit permissions, status, inviter, expiry, and revocation metadata. Maintain `invitations` as pending offers; accepting an invitation creates/activates a membership only after server validation. Do not grant access from client role labels.
4. **Separate access from billing:** use top-level `subscriptions` for a purchase tied to owner, platform, business/account, plan, provider, verified payment reference, and lifecycle dates. Use `entitlements` for the effective app/account access decision, including status, source subscription, and validity dates. An invited member inherits only the permissions of an active membership in an entitled account; they do not inherit the owner's personal subscription or need to buy a duplicate account subscription. Expired/revoked membership or entitlement removes protected access. All transitions are server-owned.
5. **Publish shared data additively:** trusted adapters write shared `moneyLedger` events keyed by `(sourceApp, sourceBusinessId, sourceRecordId)` and `customerLedger` records keyed by source customer identity. Preserve source paths and include owner, account, source, revision, deletion/reversal, and transfer/reconciliation references. Do not turn business events into personal income or expense.
6. **Centralize payments and rewards:** server-owned payment history, referral attribution/credit, subscription, entitlement, invitation, and membership operations use idempotency keys and atomic transactions. Only verified payment callbacks grant entitlements; client SDKs never mint subscription access or spend credits directly.
7. **Roll out in shadow mode:** read-only adapters first; compare event counts, source revisions, balances, transfer pairs, and customer ownership. Require owner/member isolation, expired/revoked access denial, duplicate/replay, reversal, offline/reconnect, and payment/referral double-spend tests in emulators before enabling writes.
8. **Migrate only after reconciliation:** backfill with deterministic IDs, dry-run duplicate reports, export/checksum validation, monitoring, and a rollback path. Keep legacy source records authoritative until sign-off.

## Selected shared Firestore structure

Use root collections for cross-app entities and records. Keep current app-owned records at their existing paths during rollout; shared documents are additive, server-published projections/events until reconciliation signs off on any migration. Firestore supports root collections for many-to-many relationships, and rules can authorize a request using fully specified membership-document paths; rules must still be tested against the actual client queries because they are not result filters ([Firestore data structure](https://firebase.google.com/docs/firestore/manage-data/structure-data), [security rule conditions](https://firebase.google.com/docs/firestore/security/rules-conditions), [secure queries](https://firebase.google.com/docs/firestore/security/rules-query)).

| Root collection | Canonical document and responsibility |
|---|---|
| `users/{uid}` | Shared identity/profile pointer only. Do not duplicate app-specific profile data unnecessarily. IDs are Firebase Auth UIDs within the chosen identity topology. |
| `businesses/{businessId}` | Canonical farm, retail business, or other organization. Include `ownerId`, `sourceApp`, `sourceAccountId`, display name, status, and timestamps. A Tengesa business can own several stores; store IDs remain distinct. Map each existing Murimi farm account and Tengesa business to one stable ID without deriving identity from names. |
| `accounts/{accountId}` | Financial account/scope, not an app login: `scope` is `personal` or `business`; include `ownerId`, optional `businessId`, `sourceApp`, `sourceAccountId`, currency, and status. Cash/bank/mobile-money accounts belong here; personal and business scopes remain distinct. |
| `memberships/{membershipId}` | One user’s access to one business/account. Use a stable ID derived from `(businessId, uid)`; fields include `businessId`, `uid`, `role`, explicit permission flags (including `viewFinancialSummary`), `status`, `grantedBy`, `createdAt`, `expiresAt`, and `revokedAt`. It is the authorization source; client-side role labels are never authoritative. |
| `invitations/{invitationId}` | Pending, expiring invitation with target business, inviter, invitee identity, offered role/permissions, status, and accepted/revoked timestamps. Acceptance is validated server-side and creates/activates the corresponding membership. |
| `moneyLedger/{eventId}` | Append-oriented shared financial event with stable ID from `(sourceApp, sourceBusinessId/accountId, sourceDocumentId)`. Required metadata: `id`; `ownerId`; `scope` (`personal`/`business`); `businessId` where business-scoped; financial `accountId`; `sourceApp` (`fynage`, `murimi`, or `tengesa`); `sourceModule` (`personal`, `farm`, or `store`); `sourceBusinessId`/`sourceAccountId`; `sourceDocumentId` (the source collection's document ID); `sourceRecordId` is retained as a legacy alias and must equal `sourceDocumentId`; `sourceCollection`; event `type` and `direction`; positive integer `amountMinor`; ISO `currency`; category and description; `occurredAt` (the transaction date), `createdAt`, `updatedAt`; `revision`; financial lifecycle `status` (active, reversed, or deleted/tombstoned); and `actorId`/`createdByApp`. Include optional `syncStatus` (`pending`, `synced`, or `failed`) where the source tracks it; this is transport metadata, not financial status or authorization, and per-device queue state remains in local sync metadata. Other optional fields include `toAccountId`, `transferId`, reciprocal `linkedEventId`, source payment/reference, correction `reversesEventId`/`correctsEventId`, `deletedAt`, and reason/audit metadata where applicable. Never omit the originating app/account or owner scope. Updates are versioned; corrections use adjustment/reversal events and tombstones retain history. Source apps submit through trusted adapters. |
| `customerLedger/{customerId}` | One source customer identity, with owner/business IDs, name, optional phone, source app/business/module/customer ID, and created/updated dates. Deterministic identity is source-scoped; same-name or same-phone candidates are suggested for review, never automatically merged. Restrict access to authorized business customer operations; Fynage finance summaries do not grant customer access. |
| `subscriptions/{subscriptionId}` | Purchase/history record scoped to `ownerId`, `platform`, and `accountId` or `businessId`; include plan, status, start/expiry/renewal, amount/currency, verified provider/reference, credits applied, and timestamps. One platform purchase cannot activate another platform. Server-only lifecycle writes. |
| `entitlements/{entitlementId}` | Effective access projection scoped to `(platform, accountId/businessId)`; include status, valid dates, source subscription/payment, and version. Invited users access an account through active membership plus active account entitlement; their personal subscription is separate. Server-maintained and checked on protected reads/actions. |
| `subscriptionPayments/{paymentId}` | Immutable payment attempt/verification history with provider reference, account/platform, amount/currency, status, verification timestamp, and idempotency key. Initiation is not proof of payment. Server-only status changes. |
| `referrals/{referralId}` | Referral identity and attribution. A referred UID can be attributed once; retain referrer UID, referred UID, unique code, source app, registration time, qualifying subscription/payment reference, and state. Server rejects self-referral and repeat attribution/reward. |
| `referralCredits/{creditEventId}` | Append-only credit grants and redemptions with owner UID, source referral/payment, amount, currency or credit unit, status, and idempotency key. Available balance is computed from committed events or maintained by a trusted atomic transaction; clients cannot increment or redeem directly. |

**Document identity invariant:** every Firestore document has an immutable, stable, unique document ID, mirrored by an `id` field equal to the final path segment. Source-derived ledger/customer documents use deterministic, collision-safe IDs derived from the complete source identity. Other documents receive a high-entropy ID once and persist it locally before enqueue/upload; retries and offline replay reuse that ID. Never generate a fresh ID for a retry. Validate `id == documentId` in trusted writers and rules where clients may write. Keep source record IDs in distinct fields; they do not replace shared document IDs unless safely encoded as part of the complete source identity.

Collection-specific ID rules: `users/{uid}` uses the canonical Auth UID; `businesses/{businessId}` and `accounts/{accountId}` use immutable IDs mapped to existing app accounts; `memberships/{membershipId}` is deterministic from `(businessId, uid)`; invitations and subscription attempts get a generated ID persisted before first upload/provider initiation; `moneyLedger/{eventId}` is deterministic from `(sourceApp, sourceBusinessId/accountId, sourceDocumentId)`; `customerLedger/{customerId}` is deterministic from `(sourceApp, sourceBusinessId, sourceCustomerId)`; subscription lifecycle records get stable IDs and payment provider references are stored separately; `entitlements/{entitlementId}` is deterministic from `(platform, accountId or businessId)`; `referrals/{referralId}` is deterministic from the referred UID to enforce one attribution; `referralCredits/{creditEventId}` is deterministic from the qualifying payment/referral plus grant-or-redemption type. Use a stable hash or escaped canonical encoding so delimiters, path characters, and truncation cannot create collisions.

**Duplicate prevention:** idempotency compares the complete source identity `(ownerId, sourceApp, sourceBusinessId or businessId, sourceAccountId, sourceCollection, sourceDocumentId)`, not a bare record ID. Re-importing an existing identity returns a duplicate and does not create another financial row. Remote sync uses the same identity before merging; revisions resolve updates to that same event. SMS imports additionally use a stable provider reference or message fingerprint. Similar but uncertain matches remain flagged for review and excluded from totals until resolved.

Descriptions and amounts are never transaction identifiers. Amount, direction, timestamp, and sender similarity can only produce a review suggestion; they cannot deduplicate, overwrite, or suppress an import. Automatic idempotency requires stable source identity (or an explicit provider transaction reference/message fingerprint scoped to its source).

Non-Fynage imports are rejected if `sourceDocumentId` (or the legacy `sourceRecordId`) is absent; a caller's transient shared `id` is not accepted as a substitute, because inventing or reusing an unstable ID would make retries non-idempotent. Fynage-created records generate/persist their ID at creation, and the SQLite outbox reuses that ID as the Firestore document path on each retry. Uploads transactionally compare revisions before writing, so a replay of an already-applied queued revision is a no-op.

**Ledger semantics:** a personal-to-business transfer is a linked pair of events: personal outflow and business inflow, sharing one `transferId` and reciprocal event IDs. Consolidated reporting eliminates that pair. A business sale or expense remains business-scoped and is never copied into a personal account. Imports are idempotent by source identity; deleted source records produce tombstones or reversal events rather than erasing history. `moneyLedger` grants summary-only data access where permitted; it does not expose farm batches, inventory, POS details, or customer records.

**Authorization and deployment:** financial event writes, membership changes, invitations, subscription/payment state, entitlements, and referral credits are backend-owned. Client reads are limited by owner or an active membership with the exact permission needed and by account entitlement. Root collections simplify cross-app querying but require strict rule predicates and query constraints. Server/Admin SDK adapters bypass Firestore Security Rules, so their IAM, validation, and idempotency checks are part of the trust boundary ([Firebase rule conditions](https://firebase.google.com/docs/firestore/security/rules-conditions)). Do not attach this schema to the currently mismatched projects or deploy rules until the identity topology and emulator tests are approved.
